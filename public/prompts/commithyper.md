# CommitHyper: コミットメッセージルール

> このファイルは、コーディングエージェント（Cursor, CodeWhale, GitHub Copilot 等）の
> プロジェクトルールとして、または他のルールファイルから参照されることを想定しています。
>
> **参照方法の例（別のルールファイルに追記）:**
> ```
> コミットメッセージを作成する際は、必ず @commithyper.md のルールに従ってください。
> 評価基準・良い例・悪い例は commithyper.md を参照してください。
> ```

## 基本フォーマット

```
type(scope): summary

- 変更内容の詳細（必要に応じて）
```

## type（変更の種類）

| type | 説明 |
|------|------|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `refactor` | リファクタリング（機能追加・バグ修正なし） |
| `test` | テストの追加・修正 |
| `style` | コードの意味に影響しない変更（空白・フォーマット等） |
| `chore` | ビルドプロセス・ツール・依存関係の変更 |
| `build` | ビルドシステム・外部依存関係の変更 |
| `ci` | CI設定・スクリプトの変更 |
| `perf` | パフォーマンス改善 |

## scope（省略可）

影響範囲を表す単語（`auth`, `ui`, `api`, `db`, `config`, `docs` など）。
scope を指定することで、変更箇所が一目でわかるようになります。

## summary（1行目・必須）

- **日本語で書く**
- 語尾は「〜する」「〜した」「命令形」のいずれか（**一貫性を最も重視**）
- 10〜72文字に収める
- 「何を変更したか」が具体的に伝わる内容にする

## body（2行目以降・省略可）

- サマリーの後に**空行を1行**入れる
- 箇条書き（`-`）で変更内容を整理
- 可能であれば「**なぜ**その変更が必要だったか」を含める
- 複数ファイルにまたがる変更では特に有用

## 良い例（スコア 70点以上）

```
feat(auth): GitHubログインボタンを追加する

- トップページにGitHub OAuth認証の入り口を追加
- Auth.js v5でコールバック処理を実装
- ログイン後はダッシュボードにリダイレクトする
```

```
fix(ui): ボタンのホバー色を修正した
```

```
refactor(db): クエリのN+1問題を解消する
```

```
docs(readme): セットアップ手順を追加する
```

```
feat(api): エンドポイントのレート制限を実装する
```

```
fix: ログイン時のセッション切れに対応した
```

## 悪い例（スコア 30点未満）

```
fix bug
```
→ どのバグを何のために直したか不明。typeの形式になっていない。

```
バグを修正
```
→ 日本語のみ。何をどう修正したかがまったくわからない。

```
update
```
→ 最もよくない例。変更内容が一切伝わらない。

```
WIP
```
→ 作業中であること以外、何の情報もない。

```
fix
```
→ typeのみ。変更内容がまったく不明。

## 評価基準（6項目・100点満点）

| # | 項目 | 配点 | 基準 |
|---|------|------|------|
| 1 | 形式の明確さ | 20点 | `type(scope): summary` の形式に従っているか |
| 2 | 変更種別の適切さ | 15点 | type（feat/fix等）が変更内容と一致しているか |
| 3 | Summaryの具体性 | 25点 | 何を変更したかが具体的に伝わるか |
| 4 | Why・背景の説明 | 20点 | なぜ変更したか、目的が伝わるか |
| 5 | 読みやすさ | 10点 | 1行目が10〜72文字に収まっているか |
| 6 | 追跡しやすさ | 10点 | scopeやIssue番号など、追跡に役立つ情報があるか |

**合格ライン: 70点**
